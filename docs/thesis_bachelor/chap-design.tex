\section{Architectural Overview}

The architecture keeps route files in \path{src/app} thin, screen implementations in \path{src/screens}, reusable components in \path{src/components}, services for business and integration logic, repositories for persistence, and API routes under \path{src/app/api}. This keeps the Expo Router file tree compatible with file-based routing while avoiding route-specific business logic.

\section{Capture-to-Ingest Pipeline}

The central design is deterministic: preprocess, run barcode and vision-language extraction in parallel, merge, validate, confirm, then send. Barcode detection is local and independent from provider routing. The model provider only handles image-to-JSON extraction, while the merge policy appends barcode results into a dedicated enrichment field and avoids overwriting unrelated model fields.

\begin{figure}[htbp]
  \centering
  \includegraphics[height=0.78\textheight,max width=0.95\textwidth,keepaspectratio]{artifacts/app-pipeline-activity.png}
  \caption{Activity diagram: image storage, barcode detection, extraction, merge, validation, review, submission, and queueing are represented as one end-to-end capture-to-ingest workflow.}

The flow is: user captures or imports an image, ImageStore normalizes the image and creates a thumbnail, AttemptRepository creates an attempt snapshot, barcode detection and remote extraction run in parallel, optional web-search enrichment adds manufacturer evidence, merge and validation produce a draft structured JSON object, the user edits and accepts the payload, and SubmissionService sends immediately or queues with an idempotency key.

\section{Data Model}

Each capture is represented as an attempt. Attempt records store image URIs, timestamps, status, draft JSON, accepted revision, extraction result, and error code. Queue items store serialized payloads, retry state, idempotency keys, and attempt revision. Settings store non-secret configuration, while provider and ingest secrets are routed through the secret store abstraction.

\section{User Interface Design}

The user interface is organized around four main surfaces: Capture, Confirm and Edit, History, and Settings. Capture is optimized for fast repeated scans. Confirm and Edit gives the operator visibility into structured fields, barcode evidence, and diagnostics. History provides traceability for recent attempts. Settings makes the app portable across providers and ingest environments.

\section{Security and Privacy Design}

The project requires secrets to be stored securely, HTTPS for remote calls, no telemetry by default, and diagnostics with secret redaction. Expo SecureStore encrypts and securely stores key-value pairs locally on Android and iOS, using Android Keystore-backed encrypted SharedPreferences and iOS Keychain services \cite{expo-securestore}. The production deployment should enforce HTTPS ingest endpoints and ensure that web deployments apply the same secret-handling policy appropriate to the browser environment.

\section{Architecture Model}

The design is compatible with the C4 model, which describes software architecture through hierarchical abstractions: software systems, containers, components, and code \cite{c4-model}. The project can be described as one software system containing a mobile and web application container, a local persistence container, and external model and ingest systems. Inside the application, components are represented by screens, providers, services, repositories, and API route handlers.

\section{State Model}

Attempt state is explicit. A typical attempt moves from captured to ready for review, then to sent or queued after user acceptance. Failure states distinguish extraction failure from send failure. Attempts that are sent, queued, or failed remain visible until retention pruning, while user-discarded and aborted partial attempts are removed from local history. This state model supports retry, history display, and queue replay without relying on transient UI state.
